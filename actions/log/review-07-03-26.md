# Assessment — catalogue-builder / "epac builder"

_Reviewed 2026-07-03. Core path verified by running the assembler end-to-end._

## What this is

Two apps sharing one contract (the versioned `catalogue/`):

- **Producer** (`flows/catalogue_builder/` + `definition_gen/`) — a 5-phase pipeline that turns
  Microsoft's built-in policies into the tiered catalogue. Runs occasionally, internal-only.
- **Consumer / "epac builder"** (`flows/epac_builder/`) — the customer-facing engine.
  `assemble_scaffold.py` is the sole entry point: `manifest + catalogue@version →
  EPAC/Terraform/Bicep packages`. Stdlib-only, deterministic, fail-fast. This is the scaffold
  generator the review is really about.

Invocation (verified working):

```
python flows/epac_builder/assemble_scaffold.py --manifest <c>.manifest.jsonc \
    [--input <in>.json] [--only json,terraform,bicep] [--check] [--out <dir>]
```

## State — built vs. incomplete

- **Built & solid:** full consumer pipeline (expand → validate → resolve → bind → IR → 3 renderers
  → report/lineage). Clean staged module split, real JSONC reader, hand-rolled JSON-Schema-2020-12
  subset validator, deterministic writers. Docs are unusually thorough (per-module READMEs, design
  docs, a 5-phase producer plan, naming/limits guides).
- **Built:** producer end-to-end; catalogue is generated and **committed** (version `2026.06.21`),
  with `index.json`/`catalogue.json` contract, custom overlays (naming/tagging/apim-tls), and a QC gate.
- **Incomplete / rough:** catalogue still carries `undefined`-domain policies flagged for manual
  assignment and a `builtinpolicytest` junk group; producer hard-codes an external private source
  path (`C:\GIT\Official Azure Policy\...`); no packaging (no `requirements`/`pyproject`, `sys.path`
  insert hack); `__pycache__` committed into the tree.
- **Nothing is stubbed in the core path** — the only placeholders are *intentional* `<REPLACE:>`
  values the customer is meant to fill.

## Functionality — does the core path work end-to-end?

**Yes, confirmed by running it:**

- `--check` passes on the example manifest (2 initiatives resolved).
- Full 3-flavour render produced valid packages (EPAC `Definitions/`, Terraform `azurerm` module +
  tfvars, Bicep MG-scoped `main.bicep` + params), each with a real EPAC/az CI pipeline, README,

- Every generated `.json` parses; the generated EPAC output is **byte-identical** to the committed

## Readiness — could a real customer use it today?

Not without hand-holding. The engine works, but it's alpha (commit msg literally says "alpha step 1";
flows only landed in the last few June-2026 commits). **Top 3 blockers, ranked by effort (lowest first):**

1. **No test suite / no CI on the builder** _(lowest effort, highest leverage)._ Zero automated
   coverage on an engine that emits IaC deployed to customer tenants. Determinism makes this cheap:
   drop the committed `customer/package/` in as golden fixtures, run the assembler, diff. A day of
   work buys real regression protection. (Also: add `requirements`-or-`pyproject`, drop committed
   `__pycache__`.)
2. **Manifest authoring has no completion guardrail** _(medium)._ A customer edits JSONC by hand;
   unfilled `<REPLACE:>` params and scope-less selections **pass validation and flow into output**
   (only a README note says "grep for `<REPLACE:`"). A scope-less selection emits a placeholder MG id
   Azure rejects at deploy. Add a `--strict`/pre-deploy gate that fails when any placeholder survives.
3. **Catalogue isn't customer-clean** _(highest)._ Ship a curated, finalized published catalogue:
   resolve/remove `undefined`-domain policies, drop `builtinpolicytest`, and decouple the producer
   from the hard-coded local private-repo path so the catalogue can be regenerated reproducibly.
   This is data curation + producer hardening, not a quick fix.
