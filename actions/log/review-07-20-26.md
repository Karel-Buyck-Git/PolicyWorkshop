### 1. `hierarchyVersion` is inert — the field that exists for exactly this event stayed silent

The commit reassigned 11 categories in `config/azure-domain-hierachy.md`, and `catalogue.json`'s
`inputs.hierarchyHash` moved to match (`63b8231…` → `910a106…`). But the pinned `hierarchyVersion`
stayed `2026.06.21` — **the only remaining `2026.06.21` string in the entire active tree.**

It wasn't caught because nothing reads it. `assemble_scaffold.py:107-111` verifies only
`catalogueVersion`; `hierarchyVersion` is declared in `manifest.schema.json:53-55` as "Domain
hierarchy snapshot id (lineage)" and written by `expand.py:52` as the literal
`<REPLACE: hierarchy-snapshot-id>`. A consumer reading lineage sees a hierarchy pin that silently
disagrees with the hierarchy the package was built from.

Compounding it: `lineage.json` — the provenance artifact that **ships to the customer** — records
only `catalogueVersion`. Not `contentHash`, not `builtInsRef`, not `hierarchyVersion`, not any
engine version (`pyproject.toml` is still `version = "0.0.0"`).

### 2. Phase-3 orphan bug — the mechanism, sharper than #26 originally stated

`create_initiatives.py` only ever does `group_dir.mkdir(parents=True, exist_ok=True)` (`:723`) —
append-only, no `--clean` flag, no prune anywhere in `flows/` for `initiatives/`. The damage comes
from two artifacts being derived from different universes:

| Artifact | Source | Sees a stale dir? |
|---|---|---|
| `index.json[groups]` | in-memory records parsed from markdown (`create_initiatives.py:620-638`) | **No** |
| `catalogue.json.contentHash` | `rglob("*")` over `catalogue/` on disk (`apply_overlays.py:72-80`, call `:145`) | **Yes** |

So an orphan is invisible to `index.json`, to `counts`, and to every QC check —
`quality_control.py`'s `unregistered-custom-group` (`:296-305`) is gated on `it.get("custom")`, so a
stale **built-in** group dir is skipped outright, and no reverse `index.json[groups][*].dir` → disk
check exists. Phase 5 passes green with a wrong `contentHash`, deterministically, so it never even
flaps — and `catalogue_diff.py:160` will later report drift between two semantically identical
catalogues.

**Checked whether this was ever settled deliberately: it was not.** Every mention of orphans,
wiping or GC anywhere in `actions/`, `actions/log/` or the docs is dated 2026-07-19 or later. The
prior written position was the opposite and stronger claim — `flows/catalogue_builder/README.md:9`
said each producer step "is idempotent", and `review-07-07-26.md:60` called #3 "Data curation, **not
a code fix**". Both now qualified.

**The fix pattern already exists in-tree**: `apply_overlays.py:120-128` prunes orphaned
`definitions/custom/<family>` dirs, with a comment saying it exists "so a disabled generator …
leaves no orphaned definitions behind." The reasoning was simply never applied to `initiatives/`.

### 3. Manifest tenant identifiers

`customer/manifests/.gitignore` dropped the `*.manifest.jsonc` ignore, and `NOTICE.md` +
`manifests/README.md` now instruct users to commit the manifest "for provenance". An expanded
`<customer>.manifest.jsonc` carries `tenantId`, `pacOwnerId`, `deploymentRootScope` (root
management-group resource id) and `logAnalyticsWorkspaceId` (`expand.py:47-62`). The deploy-location
decision (#24) was deliberate and stands; the open question is *where* the commit-the-manifest rule
applies — this public repo, or a customer's own private deploy repo.

### 6. QC sample-table churn

`spread()` (`quality_control.py:73-83`) picks evenly spaced **indices** from a positionally ordered
list, so inserting 17 policysets reshuffled every sample row rather than the affected ones. Net
effect in `catalogue/naming-samples.md` and `docs/epac-naming-convention.md`: Data appears twice,
Security dropped out entirely, and the `undefined-esn-ehc` row illustrating the catch-bucket is gone
— while `undefined` still holds 8 policysets. Both docs claim "a representative spread".

### 7. Unexplained provenance movement

`tools.extract` and `tools.createInitiatives` changed in `82dc38f`, which touched no Python. They
were absorbed from `da93bad` (the `--source` work), which landed after the previous regeneration in
`44ce852`. Benign, but the commit message asserts the hierarchy edit was the only input change, so
the record can't explain why provenance moved — a symptom of having no engine version to pin against.
