## Done

### #48 — the version pin is safe by default, and a label can no longer mean two things

Two decisions taken up front, both Karel's call: implement **(a) + (b)** and **reject (c)**.
Dropping the date label for a monotonic release id would have removed the collision class but
lost the customer-legible date, churned every pinned manifest, and re-opened a settled #27
decision — and #27 had *already built* the precise pin the problem actually needs. The real
defect was never the label; it was that the safe pin was opt-in and the unsafe one was default.

**(a) The default is flipped.** `expand.py` now seeds `source.catalogueContentHash` from
`catalogue.provenance()`, so every generated manifest pins the exact catalogue bytes. The
hand-authored path was the harder half: `manifest.template.jsonc` says "change VALUES only, do
NOT add keys", so a user following it *literally could not* add the precise pin. It now ships
the key as a `<REPLACE:>`, which puts the strict gate behind it — filling it is a copy-paste
from `catalogue.json`, and skipping it has to be deliberate. Deleting the line to pin by label
alone stays legal and is documented as such; the point was never to force the pin, only to stop
making the weak option the automatic one. Both schema descriptions were rewritten to match.

**(b) Two guards over one ledger.** `CHANGELOG.md` is the only artifact that records what was
actually *released* and what each label meant, which makes it the thing to check against. New
stdlib `engine/shared/changelog.py` parses it; two callers consult it:

- **`apply_overlays.py` (phase 4)** — the first point where the label *and* the contentHash are
  both known (phase 3 sets the label; phase 4 computes the hash). It refuses to finalize a label
  already released for different content, **before `catalogue.json` is written**, so the stamp
  stays `pending` — the pipeline's existing "built but not finalized" state, which phase 5 QC
  already rejects. A refused build cannot be mistaken for a good one.
- **`catalogue_changelog.py --write`** — refuses to *record* such a label (exit 2). Also now
  **skips rather than duplicates** an already-recorded identical release, which was a real
  pre-existing gap: a re-run appended a second identical entry, reading as two releases.

`--allow-version-reuse` overrides phase 4, for amending a release that never left the machine.
Phase 3 warns earlier, where `--version` is still cheap to correct. One detail worth keeping:
the suggested replacement label counts up to the first free suffix (`2026.07.26.1`) rather than
incrementing the last component — for a date label that would have silently proposed *tomorrow*.

### The guard cost a catalogue release — and #43 is what said so

Both guarded files are fingerprinted into `catalogue.json` `tools.*`, so editing them drifted
the stamp. `check_catalogue_stamp.py` reported it immediately, on the first producer change
since #43 shipped — exactly the drift class it was built for, caught in seconds instead of
sitting green for a day like the 2026-07-23 case that motivated it.

Considered moving the guard to phase 5 (`quality_control.py` is deliberately *not*
fingerprinted, so it would have cost no release) and rejected it: QC runs *after* finalize, so
the colliding `catalogue.json` would exist on disk before anything objected. Guarding at the
write is the stronger contract, and the release is the honest price.

Regenerated phases 3→4→5 and released **`2026.07.26`**, attributed to **engine**: 0 added,
0 removed, 0 re-tiered, 0 re-categorised, **3461 unchanged**. Across 193 changed files the only
non-label content change is the two tool hashes. Contoso re-pinned to both pins; all three
flavour fixtures rebuilt.

### #51 opened — the release procedure is undocumented, and that weakens #48

Karel asked for the closing flag to be explained and whether it needed a backlog row. Checking it
promoted it from an ergonomics observation to a defect, on three verified points:

- `git grep` confirmed `catalogue_changelog.py` appeared in **no document in the repo** before
  today — the tools README had neither a section nor an at-a-glance row for it. The #27/#41
  release machinery was invoked purely from `actions/sessions/*.md` narrative.
- The runbook never mentions contoso, re-pinning or fixtures, so its "Done when" is reached with
  contoso still pinned to the previous catalogue — i.e. `verify.sh` failing and CI red.
- **The part that matters:** #48's phase-4 guard compares against `CHANGELOG.md`, and
  `version_collision` returns `None` for a label the ledger does not contain. A release that is
  never recorded is therefore *invisible* to the guard and its label is silently reusable. The
  protection I shipped this session is only as strong as a step nothing tells anyone to perform.

Also measured the `MAX_PATH` trap rather than restating it: longest catalogue-relative path
**100** chars, session scratchpad root **148**, so the obvious staging location totals **259** —
one char of headroom — while `…\scratchpad\old\catalogue` is **263** and
`…\scratchpad\catalogue-<version>\catalogue` is **280**. The default choice and every sane naming
convention fail. Filed as **#51** (`low`) with those numbers and the phase-3 `rmtree` ordering
dependency written into the row; the scripted release driver is noted there as a follow-on and
deliberately kept out of scope.
