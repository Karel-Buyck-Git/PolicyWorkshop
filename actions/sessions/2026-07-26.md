### Sanity check on the taxonomy move — reverted, and the revert was worth more

Karel asked for a check on the Service Fabric → Containers placement before pushing. It came back
**against the move**, decisively, and the deciding evidence was in Microsoft's own docs metadata
rather than in the prose:

- SF is **absent** from the Azure **Containers** product category page, and **absent** from the AKS
  *Comparing container options* page (which does list Container Apps, ACI, App Service, Functions
  and OpenShift).
- Its docs carry `breadcrumb_path: ../breadcrumb/azure-compute/toc.json`, live in the
  **azure-compute-docs** repo, and are stamped `depot_name: Learn.azure-compute`.
- SF clusters run on VM Scale Sets.

The overview page's "Service Fabric is Microsoft's **container orchestrator**" line is what makes
the move look right — but that is a **capability** statement, not a category. Microsoft files the
product under Compute. **The original placement was correct**; the hierarchy was restored
byte-exact from `v0.1.0` and regenerated.

The revert paid for itself twice. It attributed cleanly to **curation** on its own (2 re-categorised
back, no upstream noise leaking in), and `inputs.hierarchyHash` **round-tripped to exactly** its
`v0.1.0` value `sha256:910a106d…` — an authored input restored to its original bytes reproduces its
original hash. That is 27e's guarantee proven from the opposite direction to the CRLF/LF test.
Phase 3's #26 self-clean left **no orphan** `containers/…/service-fabric` directory behind.

**What actually gets published: one release, `2026.07.25`, upstream-only, 0 re-categorised.** The
two intermediate taxonomy versions never left this machine, so collapsing them keeps a same-day
move-and-revert out of a customer-facing changelog for zero net change. The validation evidence
lives here and in the #41 row, which is where it belongs.

## Findings — three new rows

- **#48** (`medium`) — **`catalogueVersion` cannot distinguish two releases in one UTC day.** Hit
  for real: local time had rolled to the 26th while UTC had not, so driver (b) silently stamped
  the *same* `2026.07.25` label as (a) with different content, until hand-labelled `.1`. The gate
  is an exact string compare, so a manifest pinned to the morning catalogue builds green against
  the evening one. This is a **known** limitation — the comment at `assemble_scaffold.py:113-117`
  names it exactly and 27e added `catalogueContentHash` as the precise pin — but that pin is
  **optional and nothing defaults it on**, so the safe path is opt-in and the unsafe one is the
  default. Not a surprise defect; a defaults problem.
- **#49** (`medium`) — **`config/azure-category-abbreviation.md` is an authored input that is not
  stamped.** It feeds `shared/naming.py`, which builds *every* catalogue technical name, yet only
  three authored files are hashed into `inputs`. Edit an abbreviation and names change across the
  catalogue while no stamped input moves — `_attribute` would then report
  *"none — identical provenance (any asset drift is non-determinism)"*, sending a reader to hunt a
  phantom determinism bug. Noticed while editing that file for (a); the edit was cosmetic there
  (the lookup key is the category alone, not the domain column), which is exactly why the gap had
  gone unnoticed.
- **#50** (`low`) — **`fetch_policy_source.py` has no pin-bump mode.** It syncs *to* the pin;
  moving off it is a hand edit of `config/policy-source.json`, which is what driver (b) did.
  **#7 and #37 both assume this is a command** — an unattended runner cannot hand-edit JSON.
