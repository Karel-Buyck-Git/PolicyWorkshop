## Done

### #52a — the engine writes LF on every host

`newline="\n"` on every engine write. Consumer side (`writeutil.py`, which every renderer,
`report.py` and `package.py` write through, plus the `pacOwnerId` write-back and `--input`
expansion) is what restores the gate; `quality_control.py`, `scaffold.py` and all of
`tools/` got the same treatment so the rule is *"the engine writes LF, always"* rather than
a half-converted tree. `release.py` mattered most there — without it a bump run on Windows
rewrote `version.py` and `pyproject.toml` **entirely as CRLF**.

Also corrected the `.gitattributes` header comment, which is where this actually came from:
it asserted the file was "only about the git-stored form", but `eol=` is a *checkout*
attribute too. The wrong premise is what let the breakage ship.

**Split deliberately.** Exactly four engine files are fingerprinted into `catalogue.json`
`tools.*`, so editing them drifts the stamp and forces a regeneration — the same coupling
that cost a release in #43/#22/#48. Those four are **#52b**, batched with the next release.

**Verified:** `verify.sh` green on a Windows checkout for the first time since #45; all
three fixture trees regenerated in place produce **byte-identical** output, so the committed
fixtures never moved; stamp 9/9; MCP 5/5.

### The release driver — written straight after running the release by hand

`engine/tools/release_catalogue.py` (#51's follow-on), written immediately after Phase 6's
first manual run so it encodes where the friction *actually* was. Plan-mode by default; `--yes`
executes, `--from N` resumes.

**Both traps are enforced before anything is modified**, which is the entire point: phase 3's
`rmtree` means a late failure has already destroyed the thing you needed to diff against. It
measures the deepest path the staged copy *would* create and refuses over `MAX_PATH` — verified
at **270 chars** against the exact scratchpad location #51 measured, catalogue untouched — it
refuses to silently overwrite an existing staging copy, and it refuses a label already in
`CHANGELOG.md` naming the next free suffix. All three exit 2 before doing work.

**It does not commit, tag, push, or write the changelog's human paragraph.** Reading the diff
is a human job, and only a person can say *why* a release happened. It stops and asks.

Documented in `engine/tools/README.md` and linked from the top of Phase 6 — the one thing a
tool born out of #51 must not do is exist in no document.

### Making the driver undecayable — and closing #38 with the same change

Karel asked how the driver should *drive* a release without rotting. The honest answer is that
discipline does not scale: a monthly tool gets ~12 real executions a year while the engine
under it changes weekly, so it would be found broken **on release day** — the moment when
hand-running is fastest and the tool dies.

**The fix is coverage, not resolve.** One 3-line `EPAC_WORKBENCH_ROOT` override in
`shared/paths.py` relocates the whole workbench, and `tests/workbench.py` assembles a
throwaway one for it to point at — real `engine/`, real hierarchy/tier-rules/abbreviations,
the 4-policy fixture as source, generators rewritten per test. On that,
`tests/test_release_driver.py` now **drives a complete release on every push** in ~6s.

The same override closed **#38**: phases 4–5 had no tests *because* they read fixed paths, so
testing them meant writing to the real `catalogue/`. `test_producer_finalize.py` covers the
overlay path, the finalize stamp, **#48's collision guard at the phase level**, and phase 5's
`catalogue-not-finalized` gate. **174 tests**, all five producer phases covered, row closed —
and with it the fourth of five alpha gates.

**Two deliberate design points.** The rehearsal passes `--no-battery`, because CI already runs
those four commands directly; what nothing else covers is the *sequence*, in particular that
staging happens **before** phase 3 destroys what it stages. And `--no-battery` prints a loud
**NOT VERIFIED** banner, since a release nothing has verified is not a release.

**The anti-drift half.** Scripting the procedure created a second source of truth — the
driver's `STEPS` and the runbook's Phase 6 prose — which is #51/#53's own failure mode one
level up. So `STEPS` is the authority for *order*, the runbook owns the *why* and the traps,
and `TestRunbookAndDriverAgree` fails if a step lives in one and not the other. The policy
that keeps it alive is written into both: **if the driver fails, fix the driver and re-run —
do not finish the release by hand.**

**#56, found on the way.** Phase 5 named the producer phases with circled digits (`①`–`⑤`)
inside finding messages, and a Windows cp1252 console cannot encode them — so printing an
error-level finding raised `UnicodeEncodeError` and buried the finding under a traceback.
Only when there *was* an error to report; i.e. exactly when the operator needed to read it,
and exactly what the driver would surface mid-release. The gate itself was always correct.
Fixed (stdout/stderr reconfigured to UTF-8 with `errors="replace"`), no regeneration needed
since `quality_control.py` is not fingerprinted, and regression-guarded. Same family as #55:
a real condition arriving as a traceback instead of the message it was meant to deliver.
