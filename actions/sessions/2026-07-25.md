### #46 — the diff can no longer invent catalogue history (`cbdbc1a`)

Opened **and closed** the same session, on Karel's call: #41 is meant to validate the changelog
machinery, so that machinery had to be trustworthy first. `catalogue_diff.scan()` dropped any
policyset it failed to parse — and a dropped policyset is not neutral: every policy inside it

Caught live: generating the `2026.07.24` entry, the tool reported **"39 policies added"** for a
shape-only change that added none, because the staged old catalogue crossed the Windows 260-char
`MAX_PATH` limit. `scan()` now returns `(idx, n_policysets, failures)`; `diff_catalogues` raises
`UnreadableCatalogue` naming the count, the offenders (relative to the root, with `OSError`'s
path-repeating `str()` stripped so a 120-file list stays legible) and the `MAX_PATH` cause —
including the dead end that cost time here: **the `\\?\` prefix does not help, it stops `rglob`
matching**. `catalogue_diff.py` gets `--allow-unreadable` for a knowingly damaged tree;
`catalogue_changelog.py` deliberately does **not** — a console report is read once, a committed
entry is a durable claim.

### Clarified how the catalogue version pin actually behaves (no code change)

Karel challenged the phrase "breaks manifests" from the #47 discussion. Established from
`assemble_scaffold.py:107-124`, and worth recording because **#15's framing rests on it**:

- The pin is `source.catalogueVersion` in the **customer manifest** (`<customer>.manifest.jsonc`),
  **not** a schema — `manifest.schema.json` only declares it as a free-form string, and `source`
  requires just `initiatives`, so the pin is **optional** and an absent pin is not gated at all.
- The gate is an **exact string comparison**. No range, no "newer is acceptable". On mismatch it
  raises `AssemblerError`, prints the pinned-vs-actual pair, and **exits 2 before any rendering** —
  so a build cannot end up half-written.
- The value is a **date-shaped label for a batch, not a timestamp**: it comes from
  `create_initiatives.py --version`, defaulting to the UTC date of that run. `catalogue.json`
  does carry a true `generatedAt` timestamp, but **nothing pins or checks it**. The label is also
  deliberately not unique — a regen at the same `--version` keeps it while content moves, which is
  why 27e added the separate optional `source.catalogueContentHash` pin.
- **Nothing in this repo is affected today**: contoso is re-pinned to `2026.07.24`, the template
  holds the `<REPLACE: catalogue-snapshot-id>` placeholder, and `customer/` has no committed
  manifest. The exposure is a manifest living in a *consumer's own* repo.
- Found while checking, **not opened as a row**: `customer/manifests/README.md:52` documents the
  pin with a stale `2026.06.10` example and says it "must match `catalogue/catalogue.json`", but
  the value is read from `index.json` (`catalogue.py:41`).

  catalogue is now `2026.07.24`, and the assembler **refuses to build** on a
  `source.catalogueVersion` mismatch (exit 2, before rendering). A manifest still pinned to
  `2026.07.18` — including a real customer's committed package — will not build until that one
  string is re-pinned. Contoso was updated here because it is a fixture; a real consumer has no
  upgrade procedure, which is exactly **#15**. This is the first time the repo has produced a
  second catalogue version, so #15 moved from theoretical to due.

  already-built package, and the gate aborts before writing anything. The fix is a one-line
  re-pin. What is genuinely missing is the *procedure telling a consumer to do that*, which is the
  whole of #15. See "Clarified how the catalogue version pin actually behaves" under Done.
