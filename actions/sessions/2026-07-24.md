`CUST_DEFAULT` `dlw`→neutral `org` (raw-catalogue fallback only). Catalogue regenerated pinned to

### #27 — versioning & branching model (decision spike + all five slices landed)

Worked the spike through with Karel and resolved it. **Model: one catalogue version; provenance
carried forward + change communicated by attribution, not a second version number.** Decisions:
engine version = SemVer derived **automatically from Conventional-Commit prefixes** via an in-repo
stdlib script (no third-party tool, `dependencies=[]` preserved); **trunk-based**, version stamped at
build/release, never derived from a branch name; **retire** the inert `hierarchyVersion` (the hierarchy
is an input fully captured by the catalogue stamp). The review also exposed a **live bug**: #26 changed
`create_initiatives.py` on 2026-07-23 but never regenerated the catalogue, so the committed
`tools.createInitiatives` hash was stale for a day — nothing checks catalogue-vs-engine sync, which is
exactly what **#8** is for.

All five slices landed on `alpha/epac-builder/versioning-27` (commit `72fb799`):
- **27a** — `engine/shared/version.py` (`__version__ = 0.1.0`, static constant → byte-reproducible
  artifacts), `pyproject` `0.0.0`→`0.1.0`, `producedByEngine` stamped into `catalogue.json`, and
  `engine/tools/release.py` (stdlib auto-SemVer; `--apply --tag` does write→commit→tag in order).
- **27b** — `Catalogue.provenance()` reads `catalogue.json`; `lineage.json` now stamps
  `engineVersion, catalogueVersion, catalogueContentHash, builtInsRef, hierarchyHash` (+ `report.md`).

  Markdown entry into `catalogue/CHANGELOG.md` (seeded with the `2026.07.18` baseline). Feeds #15.
