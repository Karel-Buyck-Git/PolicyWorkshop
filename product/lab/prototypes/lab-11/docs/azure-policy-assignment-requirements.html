1. Can I assign this policy? — decision flow

Use this flow before assigning any policy or initiative. Work through each step in order.

1. Does the policy have required parameters?
Yes →
Gather prerequisite resource IDs before proceeding
↓ No
2. Is the effect Modify or DeployIfNotExists?
Yes →
Configure managed identity with required role at scope
↓ No
3. Is the policy applicable to this environment?
No →
Disable, exempt, or exclude from initiative
↓ Yes
4. Assign the policy
Then →
Trigger remediation tasks (Modify / DINE only)
Steps 1 and 2 may both apply to the same policy. A DINE policy that also requires a privateDnsZoneId needs both a prerequisite resource and a managed identity.

2. Overview

This document captures the essential knowledge required to correctly assign Azure Policy definitions in an Enterprise Policy as Code (EPAC) deployment. It covers policy effects, behavioral differences, assignment prerequisites, managed identity requirements, remediation mechanics, compliance evaluation timing, initiative vs individual assignment trade-offs, and parameter dependencies.

The goal is to give consultants and engineers a single reference that answers the question: what do I need to have in place before I can assign this policy?

3. Policy effects and behavior

Every Azure Policy definition has an effect that determines what the policy engine does when a resource is evaluated.

3.1 Effect reference

EffectWhen it firesReq. managed identitySupports remediationNotes
DenyAt request time (preflight)NoNoBlocks non-compliant deployments; cannot fix existing resources
AuditPost-deployment evaluationNoNoFlags non-compliant resources; no action taken
AuditIfNotExistsPost-deployment evaluationNoNoFlags when a related/child resource does not exist
AppendAt request time (inline)NoNoAdds fields to the request; uses caller identity; no backfill possible
ModifyPost-deployment + remediationYesYesPatches resource properties via operations array; no ARM template needed
DeployIfNotExistsPost-deployment + remediationYesYesDeploys child/related resource via embedded ARM template
DisabledNeverNoNoPolicy inactive; no evaluation or compliance impact
ManualManual attestationNoNoRequires human attestation; lowest hardening rank

Key insight: Only Modify and DeployIfNotExists require a managed identity on the policy assignment itself. All other effects either fire inline using the caller's identity (Append) or only evaluate without acting.

3.2 Effect hardening rank

When selecting which effect to use from a policy's allowedValues, use this rank to choose the most restrictive effect the customer environment supports:

  1. Deny (7) — most restrictive
  2. Modify (6)
  3. DeployIfNotExists (5)
  4. AuditIfNotExists (4)
  5. Audit (3)
  6. Append (2)
  7. Manual (1)
  8. Disabled (0) — policy inactive
The soft value is the least restrictive non-Disabled effect. Use it when a customer is not yet ready to enforce but wants visibility. The hardened value is the target state for a fully governed environment.

3.3 Why some policies only allow DeployIfNotExists or Disabled

Certain policies are remediation-focused by design and offer no Audit option. Example: Configure Private Link for Azure AD to use private DNS zones (7e4301f9). Its only action is deploying a privateDnsZoneGroups child resource — auditing without deploying serves no purpose.

4. Compliance evaluation cycle

Understanding the full cycle from trigger to remediation is essential for setting customer expectations.

4.1 Full cycle for Modify and DeployIfNotExists

  • Policy assigned — evaluation triggers within 15–30 minutes for new resources, up to 24 hours for a full scan of existing resources
  • Policy engine evaluates the if condition against each resource in scope
  • For DINE: checks the existenceCondition — is the related resource present in the expected state?
  • Non-compliant resources are flagged in the compliance view
  • Remediation task is triggered manually or via automation
  • Managed identity issues PATCH (Modify) or ARM deployment (DINE) against each non-compliant resource
  • Policy engine re-evaluates — resources become compliant once the operation succeeds
  • Compliance score updates within the next evaluation cycle (up to 24 hours for full propagation)

4.2 Full cycle for Deny, Audit, and Append

  • Deny: all subsequent deployment attempts that violate the policy are blocked at request time; existing non-compliant resources are flagged but not blocked or removed
  • Audit/AuditIfNotExists: non-compliant resources are flagged; no action taken; compliance score is affected immediately
  • Append: all subsequent deployment requests have the specified fields added inline; no effect on existing resources
For Deny policies, existing non-compliant resources are not automatically removed or blocked. They remain in place and are flagged in the compliance view. Customers must remediate them manually.

5. Assignment requirements

An assignment requirement is anything that must be in place or provided before a policy can be assigned and function correctly.

5.1 Managed identity

Policies with Modify or DeployIfNotExists effects require a system-assigned managed identity on the policy assignment. This identity performs remediation tasks after evaluation.

5.1.1 What the managed identity does

  • For Modify: issues an ARM PATCH call to update a resource property directly (e.g., set disableLocalAuth = true)
  • For DeployIfNotExists: submits the embedded ARM template to Azure Resource Manager, creating or configuring a child or related resource

5.1.2 Role requirements

The roleDefinitionIds field in the policy's details block specifies which role the managed identity needs:

  • Network Contributor — for private endpoint and DNS zone group deployments
  • Contributor — for broader resource creation such as private endpoints for App Configuration
  • Specific data-plane roles — for service-specific configurations

EPAC deployment approach: Grant the managed identity Owner or the required role at the highest management group level. This eliminates per-policy role assignment management and ensures remediation tasks can always execute.

Every ARM operation requires an identity. The distinction is whose. Append and Deny use the caller's identity (the SPN or pipeline). Modify and DINE use the managed identity on the assignment. "Requires Managed Identity" means: does the assignment itself need one configured on it?

5.2 Parameters

Any parameter without a defaultValue (and not named effect) must be supplied at assignment time.

5.2.1 Parameter taxonomy

Parameter typeExamplesBlocks assignment?Notes
NetworkingprivateEndpointSubnetId, privateDnsZoneId, vnetIdYes (no default)Resource must exist before assignment; subnet must have private endpoint policies disabled
DiagnosticslogAnalyticsWorkspaceId, storageAccountId, eventHubName, diagnosticsSettingNameYes (no default)Target sink must exist; name param controls the diagnostic setting resource name

5.2.2 The assignPermissions flag

Parameters with "assignPermissions": true cause Azure to auto-create a role assignment on that resource at assignment time. Requires Owner or User Access Administrator on the assigner. Handled automatically in the EPAC model with broad managed identity permissions.

6. Assignment scope hierarchy

The scope at which a policy is assigned determines which resources are evaluated and where the managed identity role must be granted.

Scope levelCoversMI role scopeWhen to use
Management groupAll subscriptions beneathManagement group (recommended)Enterprise-wide baseline policies; EPAC default for most assignments
SubscriptionAll resource groups in subscriptionSubscriptionSubscription-specific overrides or landing zone policies
Resource groupAll resources in the groupResource groupFine-grained control; rarely used in enterprise EPAC

6.1 Scope inheritance

Assignments inherit downward. A management group assignment applies to all subscriptions beneath it unless explicitly excluded via notScopes.

6.2 Exclusions in EPAC

{
  "nodeName": "/root/",
  "assignment": {
    "name": "baseline-security",
    "displayName": "Baseline Security Initiative"
  },
  "policySetDefinitionId": "/providers/Microsoft.Authorization/policySetDefinitions/...",
  "notScopes": [
    "/subscriptions/<sandbox-subscription-id>"
  ]
}

7. DeployIfNotExists vs Modify

7.1 DeployIfNotExists mechanics

DINE policies carry a full ARM template in their deployment block. The policy engine evaluates the if condition, checks the existenceCondition, marks non-compliant resources, and on remediation submits the embedded template via the managed identity.

DINE checks for existence but not always correctness. If a child resource exists but references the wrong configuration (e.g., a DNS zone group pointing to the wrong zone), the existenceCondition may still pass. Always read the existenceCondition in the policy JSON before trusting a compliant state.

7.1.1 Example: Configure private endpoints for App Configuration (614ffa75)

Deploys a full Microsoft.Network/privateEndpoints resource. Requires: VNet and subnet with private endpoint policies disabled, privateEndpointSubnetId parameter at assignment, Contributor role on the managed identity.

7.2 Modify mechanics

Modify policies use an operations array — no ARM template. The managed identity issues a direct PATCH to the resource ARM API.

Example: Configure App Configuration stores to disable local authentication (72bc14af). No template, no extra parameters. Patches disableLocalAuth = true directly on the resource.

8. Remediation tasks

DINE and Modify act automatically only on new or updated resources. Existing non-compliant resources need a remediation task.

8.1 How remediation works

  • Policy engine identifies all non-compliant resources in scope
  • Managed identity issues PATCH (Modify) or ARM deployment (DINE) against each
  • Resources become compliant once the operation succeeds
  • Compliance score updates within the next evaluation cycle

8.2 Remediation does not apply to

  • Deny — blocks at request time; cannot retroactively fix existing resources
  • Append — fires inline; no post-deployment action possible
  • Audit and AuditIfNotExists — evaluate only; no action taken
The effects that support remediation (Modify + DINE) are exactly the same set that require a managed identity. The managed identity is the remediation mechanism.

9. Initiative vs individual assignment

Managed identityOne identity per assignmentOne identity for the entire initiative assignment

EPAC patternpolicyAssignments/*.jsonc with policyDefinitionIdpolicyAssignments/*.jsonc with policySetDefinitionId

9.1 When to use individual assignments

  • Testing a single policy before broad rollout
  • A policy has a unique scope or exclusion differing from the rest of the initiative
  • You need to exempt a specific policy without affecting the entire initiative

9.2 When to use initiative assignments

  • Grouping related governance controls — all network hardening, all diagnostic settings, all tag enforcement
  • Applying a benchmark such as the Microsoft Cloud Security Benchmark
  • Multiple DINE/Modify policies share the same managed identity — one initiative covers all
  • Parameter reuse — a single logAnalyticsWorkspaceId feeds multiple policies

9.3 EPAC initiative assignment structure

{
  "nodeName": "/security/",
  "assignment": {
    "name": "network-hardening",
    "displayName": "Network Hardening Initiative"
  },
  "policySetDefinitionId": "/providers/Microsoft.Authorization/policySetDefinitions/<id>",
  "parameters": {
    "privateDnsZoneId": "/subscriptions/.../privateDnsZones/privatelink.vaultcore.azure.net",
    "privateEndpointSubnetId": "/subscriptions/.../subnets/pe-subnet",
    "effect": "DeployIfNotExists"
  },
  "managedIdentityLocations": {
    "westeurope": ["/providers/Microsoft.Management/managementGroups/<mg-id>"]
  }
}

10. Handling non-applicable policies

10.1 Set effect to Disabled

If allowedValues includes Disabled, set effect to Disabled at assignment. No evaluation, no compliance impact. Best when a service is definitively out of scope.

10.2 Create a policy exemption

  • Waiver — no intention to comply with this control
  • Mitigated — a compensating control addresses the risk

Exempted resources are excluded from the compliance score. Exemptions can be time-bounded.

10.2.1 EPAC exemption structure

{
  "nodeName": "/exemptions/",
  "exemptions": [
    {
      "name": "no-private-link-appconfig",
      "displayName": "Private Link not required for App Configuration",
      "description": "Customer does not use App Configuration; policy not applicable",
      "exemptionCategory": "Waiver",
      "policyAssignmentId": "/providers/Microsoft.Management/managementGroups/<mg>/providers/Microsoft.Authorization/policyAssignments/<name>",
      "policyDefinitionReferenceIds": ["614ffa75-862c-456e-ad8b-eaa1b0844b07"],
      "scope": "/subscriptions/<subscription-id>"
    }
  ]
}

10.3 Compliance score impact

  • Disabled — no evaluation; excluded from score
  • Exemption — excluded from score for exempted resources
  • No matching resources — policy shows not applicable; no score impact
  • DINE/Modify with non-compliant resources — counted against score until remediation task runs

Behavioral groups

Add / Add or replace (Modify): Apply a tag with a specific value. Supports remediation. Add or Replace overwrites an existing value; Add does not.

Append: Adds a tag field inline at request time using the caller's identity. Cannot backfill existing resources. No managed identity on the assignment.

Inherit (Modify): Copies a tag from parent scope. Supports remediation. Only tagName required — value is derived from the parent at runtime.

Require (Deny): Blocks resource creation if the tag is absent. Cannot fix existing resources. No managed identity.

For multiple mandatory tags, wrap policies in a custom initiative — one policy per tag. Single assignment, all tag names and values as initiative parameters.

12. EPAC deployment checklist

12.1 Per policy

  • Read allowedValues for effect — choose the hardened value the customer supports
  • Identify all non-effect parameters without a defaultValue — must be supplied
  • If effect is Modify or DINE — ensure managed identity has required role at correct scope
  • Verify prerequisite resources exist before assignment
  • Review the existenceCondition for DINE policies — confirm it checks what you expect
  • If not applicable — decide: Disabled, exemption, or exclude from assignment

12.2 Per initiative

  • Map policy required parameters to initiative-level parameters
  • One managed identity covers all Modify/DINE policies in the initiative
  • After assignment, trigger remediation tasks to bring existing resources into compliance
  • Set notScopes for any excluded subscriptions or resource groups

13. Key concepts summary

  • Effect determines everything: timing, identity requirements, remediation capability, and compliance score impact
  • Managed identity equals remediation capability: only Modify and DINE need it; they are also the only effects that support remediation tasks
  • Required parameters block assignment: any non-effect parameter without a defaultValue must be supplied; no role assignment substitutes for a missing resource ID
  • DINE has an embedded ARM template; Modify does not: Modify uses an operations array to patch resource properties directly
  • existenceCondition checks presence, not always correctness: a misconfigured child resource may pass silently; always read the condition before trusting compliance state
  • Remediation is always opt-in for existing resources: DINE and Modify only act automatically on new or updated resources; existing non-compliant resources need a remediation task
  • Compliance propagation takes up to 24 hours: initial evaluation triggers within 15–30 minutes; full scans and score updates can take up to 24 hours
  • Initiatives reduce operational overhead: one assignment, one managed identity, shared parameters — prefer initiatives for related governance controls
  • Scope at management group covers everything beneath: use notScopes to exclude; grant managed identity role at the same scope or higher
  • Non-applicable policies do not hurt your score: if no resources match the if condition the policy is neutral; use Disabled or exemptions to formally document intent
  • Tag policies always require customer input: tagName and tagValue are environment-specific; use a custom initiative for multiple mandatory tags
