# Cosmos DB Policies

## Tier Rationale

**Essential — Identity, key rotation, and data-plane lockdown.**
Cosmos DB is a planet-scale data store; a leaked account key or an open firewall is an exfiltration event. The baseline removes the legacy attack patterns: local authentication disabled in favour of Microsoft Entra ID, account keys forcibly rotated within a maximum age, key-based metadata writes blocked, the wildcard 0.0.0.0 "all Azure datacenters" firewall rule disallowed, allowed deployment regions constrained for data-residency, and throughput caps in place so a runaway autoscale doesn't become a billing or capacity incident. These map to ISO 27001 A.5.15 (access control), A.5.17 (authentication information), and the CIS Microsoft Azure Foundations Benchmark NoSQL recommendations.

**Professional — Firewall enforcement, public access closed, threat detection on.**
At this tier the account is no longer reachable from the public internet by default: firewall rules are required (or public access is disabled), and Microsoft Defender for Azure Cosmos DB (advanced threat protection) is deployed so anomalous query patterns and suspicious access attempts are surfaced for the security team to act on. The "someone has to act on findings" requirement is what places Defender at Professional rather than Essential — it addresses NIS2 Article 21(2)(b) incident handling.

**Enterprise — Private link, customer-managed keys, zero-trust connectivity.**
Enterprise customers route Cosmos DB traffic exclusively through Private Link / Private Endpoints with Private DNS zones (no public DNS, no public route), and encrypt at rest with customer-managed keys held in Key Vault, providing full key-lifecycle control. This combination meets ISO 27001 A.10/A.8.24 (cryptography), NIS2 Article 21(2)(h) cryptography and key management, and the data-sovereignty obligations common to financial services, healthcare (HIPAA), and EU public-sector workloads.
