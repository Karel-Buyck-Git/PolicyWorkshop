# Data Factory Policies

## Tier Rationale

**Essential — Identity, secrets in Key Vault, scoped linked services.**
Data Factory moves data between systems, so the baseline removes the obvious leakage paths: linked services must use system-assigned managed identity for authentication wherever supported (no inline credentials), secrets must be stored in Key Vault rather than in linked service definitions, allowed linked-service types are restricted to control the boundary of data movement, integration runtime cores are capped for cost control, and the factory uses Git only on the dev factory (not on test/prod, which should deploy via CI/CD). These map to ISO 27001 A.5.15 (access control), A.8.5 (secure authentication), and A.8.7 (protection against data leakage).

**Professional — Public access closed, VNet-integrated SSIS, outbound allowlists.**
At this tier the factory is no longer accessible from the public internet by default, SSIS integration runtimes are joined to a VNet for isolated execution, and pipelines are restricted to communicate only with an allowed list of domains to prevent token and data exfiltration. Operations must own the VNet, the allowed-domain list, and the response when a legitimate pipeline needs a new outbound target. This aligns with NIS2 Article 21(2)(d) supply-chain security and CIS Microsoft Azure Foundations Benchmark recommendations on data movement services.

**Enterprise — Private link, customer-managed keys, full DNS isolation.**
Enterprise customers route Data Factory exclusively through Private Link / Private Endpoints with Private DNS zones (no public DNS resolution, no public route), and encrypt the factory metadata at rest with customer-managed keys held in Key Vault with full key-lifecycle control. This combination meets ISO 27001 A.10/A.8.24 (cryptography), NIS2 Article 21(2)(h) cryptography and key management, and the data-sovereignty obligations common in regulated data-integration scenarios (finance, healthcare, public sector cross-border data flows).
