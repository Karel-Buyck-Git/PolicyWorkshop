# Container Registry Policies

## Tier Rationale

**Essential — Entra-only authentication and no anonymous pulls.**
The container registry is the source of every image that runs in your environment; a compromised registry is a supply-chain compromise. The baseline disables every legacy authentication path — admin user, repository-scoped access tokens, anonymous pull, and ARM-audience tokens — forcing Microsoft Entra ID authentication for both push and pull, and blocks cache rule creation so pull-through caches cannot smuggle in unvetted upstream content. These map to ISO 27001 A.5.15 (access control), A.8.5 (secure authentication), and NIS2 Article 21(2)(d) supply-chain security.

**Professional — Network access constrained, exports disabled.**
At this tier the registry is no longer reachable from the public internet by default: unrestricted network access is blocked (requiring firewall rules or private endpoints), public network access is disabled, and image exports are turned off so data cannot leave via `acr import` or `acr transfer`. Operations must own the firewall allowlist and the export-control posture. This addresses CIS Microsoft Azure Foundations Benchmark §9 (registry) recommendations and NIS2 Article 21(2)(d) supply-chain controls.

**Enterprise — Private Link, customer-managed keys, Premium SKU.**
Enterprise customers run the registry on the Premium SKU (required for Private Link), route every pull through Private Endpoints with Private DNS zones (no public DNS resolution), and encrypt the registry contents with customer-managed keys held in Key Vault with full lifecycle control. This combination meets ISO 27001 A.10/A.8.24 (cryptography), NIS2 Article 21(2)(h) cryptography and key management, and the supply-chain-integrity expectations of regulated industries running container workloads.
