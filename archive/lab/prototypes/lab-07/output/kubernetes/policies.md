# Kubernetes Policies

## Tier Rationale

**Essential — Entra integration, workload identity, KMS-encrypted etcd, auto-upgrade, OPA Gatekeeper.**
AKS clusters host containerized workloads that often handle production traffic and credentials, so the baseline focuses on closing the classic Kubernetes attack paths: Microsoft Entra ID integration with Kubernetes RBAC (no local Kubernetes accounts), local authentication methods disabled, managed identities for both cluster and workloads (workload identity binds pod-level identities to Azure resources), KMS encryption for etcd at rest (the secret store), SSH on nodes disabled, command-invoke disabled (it bypasses restricted network access and Kubernetes RBAC), Azure Policy add-on / OPA Gatekeeper installed for admission control, Image Cleaner removing stale/vulnerable images automatically, cluster auto-upgrade and node-OS auto-upgrade enabled, Azure CNI as the network plugin, and a wide range of pod-spec admission policies (no privileged containers, no hostPath, resource limits enforced, read-only root filesystem, drop capabilities, no latest-tag images, image registries restricted). These map to ISO 27001 A.5.15, A.8.5, A.8.7, A.8.8, A.8.24, A.8.28 and CIS Kubernetes Benchmark / CIS Microsoft Azure Foundations Benchmark §9.

**Professional — Defender for Containers, service mesh, GitOps, internal load balancers, anti-affinity.**
At this tier the cluster is observable and operationally hardened: Microsoft Defender for Containers (the SecurityProfile.AzureDefender agent and Arc extension equivalents) is deployed to provide environment hardening, workload protection, and runtime threat detection — someone needs to triage Defender findings, which is what places it at Professional. Open Service Mesh provides east-west traffic encryption and observability, Strimzi Kafka extension provides observability/security for streaming workloads, Flux v2 GitOps configuration enforces declarative source-of-truth from a Git repository, internal load balancers make Kubernetes services VNet-only (no public LB), and anti-affinity / topology spread constraints enforce HA scheduling across nodes. Aligns with NIS2 Article 21(2)(b) incident handling, Article 21(2)(d) supply-chain integrity, and CIS Kubernetes Benchmark §3/4 (logging and admission).

**Enterprise — Private clusters, CMK on disks, encryption at host, diagnostic pipeline.**
Enterprise customers run AKS as a private cluster (API server reachable only via the private network — no public control-plane endpoint), encrypt OS and data disks with customer-managed keys held in Key Vault (covering both the cluster nodes and any persistent volumes), enforce encryption-at-host on agent node pools (temp disk and disk caches), and stream resource logs + Azure Monitor diagnostic settings into a Log Analytics workspace for SIEM ingestion. This combination meets ISO 27001 A.10/A.8.24 (cryptography), A.12.4 (logging and monitoring), NIS2 Articles 21(2)(h) and 23 cryptography and incident reporting, and the data-sovereignty obligations of regulated container workloads (healthcare, finance, public-sector workloads with sovereignty requirements).
