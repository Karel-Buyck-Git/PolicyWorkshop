## Readiness — could a real customer use this today?

**Alpha, and the most-defensible it's been.** The engine works from a clean scaffold, onboarding is
guided (#16), and #2 now means a scope-less / unfilled-parameter manifest **fails** a `--strict` check
instead of silently emitting a package Azure rejects. Remaining blockers, ranked by effort (lowest first):

1. **Catalogue isn't customer-clean (#3)** _(medium–high)._ Now the top *product* blocker (with #2 closed):
   a customer browsing the catalogue can still select `undefined`-domain / `builtinpolicytest` entries.
   Resolve/remove them so the catalogue regenerates reproducibly. Data curation, not a code fix.
2. **Deployability never proven (#14)** _(high)._ CI proves byte-diff, not that the package passes
   `Build-DeploymentPlan`/what-if on a real tenant, nor that the generated pipeline runs. "Works" still
   means "rebuilds identically." Needs a sandbox tenant + creds → separate opt-in workflow.
3. **No catalogue-upgrade path (#15)** _(high)._ Catalogue bumps ~monthly; a package built at version X
   has no supported migration to Y. Second-customer blocker.
