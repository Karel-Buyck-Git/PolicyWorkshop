## Structure (how it actually runs)

- **One consumer entry point:** `flows/epac_builder/assemble_scaffold.py`.
  - `--input <input.json>` → expands to a manifest, then stops.
  - `--manifest <m.jsonc>` → the real build: expand → validate (2 schemas) → resolve selection →
    bind → build IR → render → report/lineage/package.
  - `--only json,terraform,bicep`, `--check` (validate only, no writes), `--out <dir>`.
  - Pipeline modules: `jsonc`, `validate`, `catalogue`, `bind`, `expand`, `ir`, `mgscopes`,
    `render_json` / `render_terraform` (+`hcl`) / `render_bicep`, `report`, `package`. Stdlib-only.
- **Producer** (`flows/catalogue_builder/*`, runbook `/catalogue-builder-run`): regenerates the
  shared `catalogue/` from Microsoft built-ins. Source is pinned/reproducible (`config/policy-source.json`
  + `flows/tools/fetch_policy_source.py`). Not on the customer path.
- **User-facing surfaces:** `/epac-builder-start`, `/epac-builder-onboard` (new), `/reset-customer-package`
  (new), `/catalogue-builder-run`. Onboarding skill at `skills/epac-builder-onboarding-agent/`.

## Readiness — could a real customer use this today?

**Alpha, and closer than 07-03/07-05-morning.** The engine works, a user starts from a clean scaffold,
and onboarding is now guided. But "the assembler is deterministic" is **not** "the package deploys."
Remaining blockers, ranked by effort (lowest first):

1. **Manifest completion guardrail (#2)** _(medium)._ Still the sharpest edge for a real user: a
   scope-less or unfilled-parameter manifest builds "successfully" and emits an EPAC package Azure
   rejects at deploy — only signal is a `[warn]`. Add a `--strict`/pre-deploy gate that fails when any
   `<REPLACE:>` or placeholder-scope survives into output.
2. **Deployability never proven (#14)** _(high)._ CI proves the byte-diff, not that the generated
   package passes `Build-DeploymentPlan`/what-if against a real tenant, nor that the generated pipeline
   runs. Until contoso is deployed against a sandbox tenant, "works" means "rebuilds identically," not
   "deploys." Needs credentials → separate opt-in workflow.
3. **Catalogue isn't customer-clean (#3)** _(high)._ Resolve/remove `undefined`-domain policies and drop
   `builtinpolicytest` so a customer never selects into junk and the catalogue regenerates reproducibly.
   Data curation, not a quick fix.
4. **No catalogue-upgrade path (#15)** _(high)._ Catalogue bumps ~monthly; a customer package built at
   version X has no supported migration to Y. Not a day-one blocker, but a here-comes-the-second-customer
   blocker.
